# План: домашний каталог вещей и поиск по коробкам

## 1. Цель и границы первого релиза

Сделать адаптивное PWA-приложение для учёта домашних вещей: пользователь быстро находит вещь, видит её фото, текущую коробку и место этой коробки, а также просматривает историю перемещений и состава.

**MVP включает:**

- регистрацию и вход, с глобально включаемой/выключаемой регистрацией;
- несколько независимых «пространств хранения» (например, «Квартира на Лесной», «Дача»), с участниками и ролями;
- иерархию мест внутри пространства: «Балкон → стеллаж → верхняя полка»;
- коробки, их текущие и временные места;
- вещи с обязательным хотя бы одним фото, опциональными описанием и тегами;
- полнотекстовый поиск с карточками-предпросмотрами;
- неизменяемую историю важных изменений;
- светлую/тёмную темы, офлайн-оболочку и установку PWA;
- постоянную кнопку добавления, адаптированную для телефона.

**Не включать в MVP:** распознавание объектов на фотографиях, QR/штрихкоды, совместное редактирование в реальном времени, публичный доступ по ссылке, уведомления, экспорт/импорт. Их заложить в модель и API без реализации интерфейса.

## 2. Термины домена

В исходной постановке слово «локация» используется для двух разных сущностей. В продукте их следует разделить:

| Термин в интерфейсе | Техническое имя | Пример | Назначение |
|---|---|---|---|
| Пространство хранения | `storage_space` | «Квартира на Лесной», «Дача» | Граница доступа: владелец, участники, описание, адрес |
| Место | `location` | «Балкон», «Прихожая», «Коробки под кроватью» | Дерево мест внутри пространства; здесь физически лежат коробки |
| Коробка | `box` | «Зимняя одежда» | Контейнер вещей с текущим/временным местом |
| Вещь | `item` | «Синие лыжные перчатки» | Единица поиска и учёта |

Название пространства не уникально: устойчивый URL и связи строятся по UUID/slug, а не по отображаемому имени.

## 3. Техническое решение

Выбрать модульный монолит: он даёт простую поставку и транзакционную целостность историй без преждевременного разделения на сервисы.

| Слой | Решение | Причина |
|---|---|---|
| Backend | Go, стандартные `net/http` и `http.ServeMux` | явный HTTP API, малый набор зависимостей, простая поставка в контейнере |
| Frontend | React + TypeScript strict + Vite | отдельный быстрый SPA-клиент, пригодный для PWA и независимой поставки |
| UI | Tailwind CSS, shadcn/ui, Radix primitives, Lucide | чистая нейтральная стилистика уровня Vercel/Notion, доступность, темы |
| Client state/API | Redux Toolkit + RTK Query (`trk-query` в исходном требовании) | предсказуемое состояние, кэш, инвалидация и optimistic updates для REST API |
| Формы/валидация | React Hook Form + Zod; серверная валидация в Go | удобные формы без доверия данным клиента |
| БД | PostgreSQL | транзакции, поиск, надёжное хранение истории |
| SQL/доступ к БД | `pgx/v5` + Squirrel (`sqwirrel` в исходном требовании) | быстрый драйвер PostgreSQL, параметризованные запросы и прозрачный SQL без ORM |
| Миграции | golang-migrate | версионируемые SQL-миграции, запускаемые отдельным job/контейнером |
| Аутентификация | собственные email/password-сессии в PostgreSQL + Argon2id | HTTP-only cookie, полный контроль registration toggle и ролей |
| Файлы | MinIO локально и S3-совместимое object storage в production | фото не попадают в БД и легко масштабируются |
| Изображения | Go image-processing worker/пакет + `<img>`/responsive `srcset` | thumbnails/webp/avif без привязки к Next.js |
| Поиск | PostgreSQL FTS (`tsvector`) + `pg_trgm` | поиск по названиям, описаниям, тегам и коробкам без отдельного сервиса |
| PWA | manifest + service worker через Serwist | установка, cache оболочки, очередь не нужна в MVP |
| Тесты | Go `testing` + Testcontainers-Go; Vitest, Testing Library, Playwright | unit/integration/E2E и реальный PostgreSQL в CI |
| Развёртывание | Docker Compose + CI (GitHub Actions) | одинаковые локальная, тестовая и production среды |

Репозиторий — два независимых приложения в одном Git-репозитории: `backend` (Go module) и `frontend` (pnpm/Vite). Общий API-контракт хранится в `api/openapi.yaml`, генерируемые TypeScript-типы — в `frontend/src/api/generated`; это исключает расхождение форматов Go API и RTK Query.

## 4. Архитектура и структура

Использовать feature-first структуру. React не обращается к БД и не хранит auth-токены: он вызывает JSON HTTP API через RTK Query с `credentials: 'include'`. Доменные операции выполняются Go use-case'ами и в одной транзакции записывают состояние и событие истории.

```text
api/
  openapi.yaml                       # REST-контракт и генерация TypeScript-типов
backend/
  cmd/api/main.go                     # composition root и HTTP server
  internal/
    auth/                             # password/session/cookie middleware
    domain/                           # сущности, политики, ошибки
    feature/                          # auth, spaces, locations, boxes, items, search, media
    httpapi/                           # handlers, DTO, middleware, роуты net/http
    repository/postgres/              # pgx + Squirrel, SQL-запросы
    service/                           # use-cases и транзакции
    storage/                           # MinIO/S3 client
  migrations/                         # SQL для golang-migrate
  Dockerfile
frontend/
  src/
    app/                              # Redux store, router, providers
    api/                               # RTK Query base API и generated types
    features/                          # auth, spaces, locations, boxes, items, search
    components/ui/                    # shadcn primitives
    components/layout/
    pages/
    styles/
  public/                             # manifest, PWA icons
  vite.config.ts
  Dockerfile
deploy/
  nginx/                              # same-origin reverse proxy в production
docker-compose.yml
```

Правила:

1. Каждый запрос всегда фильтруется по `storage_space_id` и проверяет членство в Go middleware/service до выполнения repository-запроса.
2. Изменение состояния проходит через use-case (`moveBox`, `assignItemToBox`, `archiveItem`), а не через общий CRUD.
3. Запись истории создаётся в той же PostgreSQL-транзакции, что и изменение.
4. Фото загружаются по ограниченному presigned URL MinIO/S3; Go API подтверждает связь с сущностью только после проверки metadata.
5. UUID — внешние идентификаторы. Внутренние URL не раскрывают последовательные ID.

## 5. Модель данных

Во всех основных таблицах: `id UUID`, `created_at`, `updated_at`; в сущностях, поддерживающих мягкое удаление, также `deleted_at`, `deleted_by`.

### Пользователи и доступ

- `user`: `id`, `username` (уникальный, case-insensitive), `display_name`, `avatar_media_id?`, `status?`, `password_hash`, `email?`, auth-поля и timestamps.
- `session`: `id`, `user_id`, `token_hash`, `expires_at`, `created_at`, `last_seen_at`, `revoked_at?`, `ip_hash?`, `user_agent?`.
- `storage_space`: `id`, `name`, `description?`, `address?`, `owner_user_id`, `archived_at?`.
- `membership`: `storage_space_id`, `user_id`, `role` (`owner | admin | editor | viewer`), `joined_at`, `left_at?`; уникальность активного членства.
- `app_setting`: `registration_enabled boolean`; доступен только системному администратору/deployment-конфигурации. При выключенном флаге экран регистрации отвечает 404/403, а API также отвергает регистрацию.

### Места и коробки

- `location`: `id`, `storage_space_id`, `parent_location_id?`, `name`, `code?`, `description?`, `cover_media_id?`, `icon`, `sort_order`, `state`, `deleted_at?`.
  - `code` уникален в пределах пространства после нормализации; служит для читаемых ссылок и импорта.
  - Нельзя сделать родителем собственный потомок; глубину дерева ограничить на уровне приложения (например, 8).
- `box`: `id`, `storage_space_id`, `name`, `description?`, `cover_media_id?`, `current_location_id?`, `temporary_location_id?`, `temporary_until?`, `state`, `deleted_at?`.
  - Эффективное отображаемое место: временное, если оно задано; иначе постоянное.
  - `current_location_id` можно оставить `NULL` для неразмещённой коробки.
- `box_location_history`: `id`, `box_id`, `from_location_id?`, `to_location_id?`, `placement_kind` (`permanent | temporary`), `occurred_at`, `actor_user_id`, `note?`.

### Вещи, фото и теги

- `item`: `id`, `storage_space_id`, `name`, `description?`, `box_id?`, `state`, `deleted_at?`, `search_vector`.
- `tag`: `id`, `storage_space_id`, `name`, `color?`, `created_at`; уникальность имени в пространстве без учёта регистра.
- `item_tag`: `item_id`, `tag_id`.
- `media`: `id`, `storage_space_id`, `object_key`, `mime_type`, `byte_size`, `width?`, `height?`, `checksum`, `created_by`, `created_at`, `deleted_at?`.
- `item_media`: `item_id`, `media_id`, `position`, `is_cover`; минимум одна активная запись обязателен перед переводом вещи в `active`.
- `box_media`: `box_id`, `media_id`, `position`, `is_cover`.
- `location_media`: `location_id`, `media_id`, `position`, `is_cover`.
- `item_box_history`: `id`, `item_id`, `from_box_id?`, `to_box_id?`, `occurred_at`, `actor_user_id`, `note?`.

### История и статусы

- `audit_event`: `id`, `storage_space_id`, `entity_type`, `entity_id`, `action`, `actor_user_id?`, `occurred_at`, `payload jsonb`.
  - `payload` хранит минимальный снимок «до/после» и контекст. События append-only, не редактируются и не удаляются через приложение.

Статусы не следует моделировать набором пересекающихся boolean-флагов. Для `item`, `box`, `location` использовать:

- `active` — обычный доступный объект;
- `temporarily_unavailable` — объект существует, но временно не доступен/убран; причина и ожидаемая дата опциональны в metadata;
- `archived` — больше не участвует в обычном поиске, но сохраняется в истории;
- `deleted` — мягко удалён (`deleted_at`); исключается из обычного UI, может быть восстановлен администратором.

`deleted` — не значение рабочего `state`, а производное от `deleted_at`. Это предотвращает противоречие вида «archived и deleted одновременно». Для «временно убранной» коробки важнее использовать `temporary_location_id`, а не `temporarily_unavailable`, если её фактическое место известно.

## 6. Авторизация и правила доступа

| Операция | owner | admin | editor | viewer |
|---|---:|---:|---:|---:|
| Смотреть каталог и историю | ✓ | ✓ | ✓ | ✓ |
| Добавлять/редактировать вещи, коробки, места | ✓ | ✓ | ✓ | — |
| Перемещать и архивировать | ✓ | ✓ | ✓ | — |
| Восстанавливать удалённое | ✓ | ✓ | — | — |
| Управлять участниками | ✓ | ✓ (кроме owner) | — | — |
| Менять владельца/удалять пространство | ✓ | — | — | — |

Приглашение в пространство — через одноразовую ссылку с TTL; email-уведомления можно не делать в MVP: ссылку копирует владелец. Отзыв участника не удаляет его исторические события: в timeline сохраняется имя-снимок автора.

## 7. Пользовательские сценарии и экраны

### Навигация

- **Мобильный:** нижняя навигация «Поиск», «Коробки», «Места», «Ещё»; плавающая `+`-кнопка всегда в нижней безопасной зоне.
- **Desktop:** боковая панель выбора пространства, ссылки на разделы, глобальный поиск, пользовательское меню; `+ Добавить` закреплена в шапке.
- По нажатию `+` открывать компактное меню: «Вещь», «Коробку», «Место», «Тег». Контекст текущего пространства подставлять автоматически.

### MVP-экраны

1. **Вход / регистрация / onboarding.** После создания пространства предложить добавить первые места и коробку.
2. **Поиск.** Одна строка поиска; фильтры: место, коробка, тег, статус, «без коробки». Результат вещи показывает фото, название, теги, цепочку `Пространство → место → коробка`. Вкладка «Коробки» показывает обложку и первые 4 фото вложений/счётчик.
3. **Вещи.** Сетка карточек, виртуализация для больших коллекций, сортировки «недавно изменённые», «название», «недавно добавленные».
4. **Карточка вещи.** Галерея (минимум одно фото), название, описание, теги, расположение, статус, timeline, действия перемещения/архивации/удаления.
5. **Коробки.** Сетка/список; карточка содержит обложку, название, эффективное место, число вещей и коллаж фото содержимого. Деталь коробки показывает состав, постоянное и временное место, историю перемещений и историю состава.
6. **Места.** Древовидный список и карточки. Деталь места показывает дочерние места, находящиеся коробки и фотографию/иконку.
7. **Пространство и участники.** Название, адрес, участники, приглашения, настройки доступа.
8. **Корзина/архив.** Отдельные фильтры и восстановление; окончательное удаление не делать в MVP.

### Поиск и предпросмотр содержимого

- Запрос ищет по `item.name`, `item.description`, названиям тегов, коробок и мест; результаты ранжируются: точное название вещи → префикс → FTS → совпадения описания.
- Поддержать русскую и английскую конфигурации FTS; `pg_trgm` использовать для опечаток и коротких фрагментов.
- Для коробки показывать `cover` коробки, если он задан; иначе коллаж из первых 4 `item_media.is_cover` активных вещей. При отсутствии фото — нейтральный placeholder.
- Индексы: GIN для `item.search_vector`, GIN trigram для нормализованных названий, B-tree для всех внешних ключей и `(storage_space_id, state/deleted_at)`.

## 8. История: обязательные события

Писать `audit_event` для: создания, изменения полей, смены фото, тегов, статуса, удаления/восстановления, переноса коробки, временного размещения и возврата, добавления/изъятия вещи из коробки, приглашения/принятия/отзыва членства.

События перемещения дополнительно записываются в специализированные таблицы истории — это ускоряет timeline и аналитические запросы. В UI показывать понятные записи, например: «Михаил переместил “Зимняя одежда” из Балкона в Прихожую, 22.09.2026 14:30».

## 9. API и серверные use-cases

Go backend предоставляет версионированный JSON REST API (`/api/v1`). Роутинг — стандартный `http.ServeMux`; handlers отвечают только за HTTP/DTO, а use-case'ы — за авторизацию, бизнес-правила и транзакции. React использует RTK Query для всех запросов; server actions не используются.

Ключевые use-cases:

- `createStorageSpace`, `inviteMember`, `changeMemberRole`;
- `createLocation`, `moveLocation`;
- `createBox`, `moveBox`, `setTemporaryBoxLocation`, `clearTemporaryBoxLocation`;
- `createItemWithMedia`, `updateItem`, `assignItemToBox`, `changeItemState`;
- `prepareMediaUpload`, `finalizeMediaUpload`, `deleteMedia`;
- `searchInventory`, `getEntityTimeline`, `restoreEntity`.

Клиент валидирует формы Zod-схемами, а сервер повторно валидирует входные DTO в Go. Ошибки возвращаются в нормализованном формате (`code`, безопасное `message`, `fieldErrors?`), а сервер логирует correlation ID без URL фотографий и чувствительных полей.

## 10. PWA, доступность, безопасность

- Manifest, маскируемая иконка, standalone display, theme-color для обеих тем.
- Cache-first для статичных ассетов и offline fallback; network-first для пользовательских данных. Не кэшировать auth-ответы и подписанные URL.
- До offline-редактирования не доходить в MVP: без сети показать последнюю безопасно закэшированную страницу и явное сообщение «для изменений нужна сеть».
- WCAG 2.2 AA: контраст, видимый focus, управление с клавиатуры, aria-label для кнопок-иконок, alt-тексты фото (по умолчанию название сущности), touch targets ≥44px.
- Лимиты upload: JPEG/PNG/WebP/HEIC после проверки сигнатуры, например до 15 MB и 20 фото на сущность за запрос; server-side resize, удаление EXIF GPS по умолчанию.
- Проверять MIME по magic bytes, владение `media` и права на пространство; ограничить rate-limit на auth, приглашения, загрузки и поиск.
- Сессия хранится только в `HttpOnly`, `Secure`, `SameSite=Lax` cookie с узким `Path=/api`; токен имеет случайное значение, в PostgreSQL хранится только его SHA-256-хэш. JavaScript не читает и не хранит токен.
- SPA и API в production публикуются на одном origin через reverse proxy. Для `POST`/`PATCH`/`DELETE` дополнительно проверять `Origin`/`Referer` и требовать кастомный заголовок `X-Requested-With`; при необходимости cross-origin режима перейти на synchronizer CSRF token, но не ослаблять CORS.
- CSP, rate limits, резервные копии PostgreSQL и object storage.

## 11. План реализации

### Этап 0 — foundation

1. Инициализировать Go module с `net/http`, `pgx`, Squirrel (`sqwirrel`), golang-migrate и frontend на React/Vite/TypeScript/Redux Toolkit/RTK Query; настроить env schema и Docker Compose с PostgreSQL/MinIO.
2. Настроить SQL-миграции, seed локального демо-пространства, генерацию API-типов из OpenAPI и CI (Go test, lint, frontend typecheck/test, integration, E2E).
3. Добавить React theme provider, shell, шрифты, базовые shadcn-компоненты и responsive tokens.

**Готовность:** `go test ./...`, `pnpm lint`, `pnpm typecheck`, `pnpm test`, Playwright smoke-test и `docker compose up` проходят в чистом окружении.

### Этап 1 — идентичность и доступ

1. Реализовать password auth на Go: Argon2id-хэширование, регистрацию с серверным feature flag, вход/выход, revoke сессий и восстановление пароля.
2. Реализовать `user`, `storage_space`, `membership`, роли и серверные guards.
3. Сделать onboarding: профиль → первое пространство → первые места.

**Готовность:** пользователь не может читать или изменять данные чужого пространства; регистрация отключается без redeploy.

### Этап 2 — каталог мест, коробок и медиа

1. Миграции для `location`, `box`, `media` и объектного storage.
2. Формы и экраны мест/коробок, вложенные места, постоянное/временное размещение.
3. Реализовать безопасную загрузку, обработку и отображение обложек.
4. Создать audit framework и историю перемещений коробки.

**Готовность:** editor создаёт коробку с фото, переносит её между местами и видит корректную историю; viewer получает 403 на мутацию.

### Этап 3 — вещи, теги и состав

1. Добавить `item`, `tag`, связи фото/тегов/коробок, бизнес-статусы и soft delete.
2. Сделать форму добавления вещи, где отправка недоступна без как минимум одного успешно подтверждённого фото.
3. Реализовать карточки, коллажи содержимого коробок, состав коробки и item/box timelines.

**Готовность:** пользователь находит вещь в карточке коробки, видит её фотографию и полный путь до места; история назначения/изъятия корректна.

### Этап 4 — поиск, PWA и polish

1. Подключить FTS/trigram, поисковые фильтры, ранжирование и пагинацию/cursor.
2. Добавить manifest/service worker/offline fallback, mobile bottom-nav и постоянное `+` меню.
3. Пройти accessibility, performance и security checklist; добавить пустые состояния и архив/восстановление.

**Готовность:** Lighthouse PWA проходит installability, поиск p95 на тестовом наборе работает в установленном мобильном приложении, keyboard/mobile сценарии проходят E2E.

### Этап 5 — поставка

1. Создать production Docker image, миграционный job и настройки secrets.
2. Настроить backup/restore runbook и мониторинг ошибок.
3. Провести staging-приёмку с реальными фото и несколькими ролями.

**Готовность:** staging разворачивается с нуля; восстановление тестовой резервной копии проверено; CI запрещает merge при падении обязательных проверок.

## 12. Тестовая стратегия и критерии приёмки

**Unit:** нормализация username/tag/code; вычисление эффективной локации; переходы статусов; role policy; построение audit payload.

**Integration (PostgreSQL/Testcontainers):** RLS/фильтрация пространства на уровне query-layer; транзакция «изменение + audit»; FTS; уникальные ограничения; история перемещений.

**E2E (Playwright):** регистрация (и блокировка при отключённом toggle), создание пространства, загрузка обязательного фото вещи, добавление в коробку, временное перемещение коробки, поиск по названию/тегу, права viewer, restore soft-deleted сущности, установка PWA.

Продукт принимается, когда:

- у активной вещи есть минимум одно доступное изображение;
- путь «вещь → коробка → место» отображается и соответствует БД;
- история не теряется и не меняется при редактировании текущего состояния;
- данные одного пространства никогда не видны участнику другого;
- мягко удалённые сущности исключены из default-поиска и восстанавливаются с историей;
- все основные действия доступны на экране шириной 360px;
- dark/light темы сохраняются и не нарушают контраст.

## 13. Решения, требующие подтверждения перед стартом

Если пользователь не задаст иное, принять следующие дефолты:

1. **Один аккаунт может быть участником многих пространств**, а пространство имеет одного владельца.
2. **Фото вещи:** минимум одно, максимум 20; именно наличие подтверждённого оригинала, не только локального preview.
3. **Удаление:** только soft delete и восстановление в MVP; физическая очистка медиа — отложенная административная задача.
4. **Временная локация:** одна активная временная локация у коробки, опциональный срок и заметка.
5. **Совместный доступ:** invite-link, роли owner/admin/editor/viewer.
6. **Языки первого релиза:** русский UI и поиск на русском/английском.
7. **Поставщик hosting:** любой Docker-compatible VPS/managed container; S3-compatible storage отделён от приложения.
